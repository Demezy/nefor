# Nefor MAG in Five Minutes

This guide assumes [MAG in Five Minutes](<../01. core/00. MAG in Five Minutes.md>).
MAG knows how to manipulate typed immutable data and produce an artifact. Nefor's
libraries use that language to define nodes, graphs, agents, commands, worktrees,
and runtime expansion. None of those are special MAG syntax.

The program below starts with one node and grows into a reusable development
workflow with dynamically many follow-up workers. Read it from top to bottom:
each section adds one ordinary functional-programming idea.

```lisp
(require "agents")
(require "core.types")
(require "nefor.actors")
(require "nefor.agents")
(require "nefor.artifact")
(require "nefor.contracts")
(require "nefor.dynamic")
(require "nefor.graph")
(require "nefor.node")
(require "nefor.shell")
(require "nefor.worktree")

;; ------------------------------------------------------------
;; 1. A node is one typed piece of work
;; ------------------------------------------------------------

;; Node I O means that runtime work accepts I and eventually produces O.
;; Constructing this value runs nothing: MAG only describes the work.
(let build-command "cargo build")
(let build
  (nefor.shell.run "build"
    (as nefor.shell.ShellScriptParams
      {:script build-command
       :cwd "tmp/mag-book-worktree"
       :timeout (nefor.contracts.timeout-ms 120000)})))

;; `build` is Node Unit ProcessResult. Its input and output fields are typed
;; connection points, not values already available while MAG compiles.
;; In a completed graph, an unfed node whose input accepts Unit receives exactly
;; one Unit activation. This includes Unit-containing sums: shell.script accepts
;; Unit | Text and can also run as a root, with no stdin. An incoming edge or an
;; explicit input message suppresses automatic activation; a fed node waits for
;; its dependency instead. Products containing Unit still need every component.
;; Only the exposed root boundary is activated, not unrelated internal actors.
(let build-input-port (get build "input"))
(let build-output-port (get build "output"))

;; An agent is the same kind of value. The finite Model vocabulary and its
;; provider/model mapping belong to the installed configuration (`agents`),
;; while Nefor owns the generic constructor. This call returns
;; Node Task (TextAnswer | AgentError).
(let explainer
  (nefor.agents.with-tools agents.resolve-model agents.standard "explainer"
    "Explain the supplied task concisely."
    nefor.actors.read-only-tools
    (type-tag nefor.contracts.Task)
    (type-tag nefor.contracts.TextAnswer)
    2))

;; ------------------------------------------------------------
;; 2. Compose nodes as ordinary values
;; ------------------------------------------------------------

;; `>>>` is left-to-right function composition for nodes. `task-source` is a
;; constant Node Unit Task: it produces the configured task when activated.
;; Its activation follows the same topology rule as every other Unit-input
;; node. Composition itself adds no display wrapper: `hello` and `explainer`
;; remain direct siblings rather than accumulating a binary staircase.
(let hello
  (nefor.actors.task-source "hello"
    "Why is typed graph composition useful?"))
(let explained (nefor.node.>>> hello explainer))

;; `*>` is the established Applicative spelling for sequencing while discarding
;; the left result. Here any successful answer deterministically starts build;
;; the agent cannot accidentally omit that step or replace its command.
(let answer
  (nefor.graph.identity "answer"
    (type-tag nefor.contracts.TextAnswer)))
(let build-after-answer
  (nefor.node.*> "build-after-answer" answer build))

;; Failures are values. `>=>` is Kleisli composition for A | E: the successful
;; TextAnswer continues into the command while AgentError passes through
;; unchanged. It is the reusable form of `choose next (identity E)` followed
;; by `>>>`.
(let explained-and-built
  (nefor.node.>=> explained
    (nefor.node.lift-result "build-result" (type-tag nefor.contracts.AgentError) build-after-answer)))

;; ------------------------------------------------------------
;; 3. Build a reusable development workflow
;; ------------------------------------------------------------

;; These are application types. Nefor does not prescribe an SDLC.
(type Approved {:summary String})
(type NeedChanges {:feedback String})
(type ReviewDecision (adt [Approved Approved] [NeedChanges NeedChanges]))
(type DevelopmentConfig
  {:id String
   :repository String
   :worktree String
   :branch String
   :base String
   :build String})

;; This function constructs its whole subgraph from its arguments. Callers see
;; only Node Task (ReviewDecision | AgentError), whether the implementation
;; contains one actor or a large graph.
(let development-workflow
  (fn [[config DevelopmentConfig]]
    -> (nefor.graph.Node nefor.contracts.Task
         (core.types.Result nefor.contracts.AgentError ReviewDecision))
    (let id (get config "id"))
    (let task-value
      (nefor.node.rename "task"
        (nefor.graph.identity (str id ".task")
          (type-tag nefor.contracts.Task))))
    (let worktree
      (nefor.node.rename "create"
        (nefor.worktree.create (str id ".worktree")
          (as nefor.worktree.CreateSpec
            {:repository (get config "repository")
             :path (get config "worktree")
             :branch (get config "branch")
             :base (get config "base")}))))
    (let worktree-trigger
      (nefor.node.rename "trigger"
        (nefor.graph.identity (str id ".worktree-trigger")
          (type-tag nefor.contracts.Task))))
    (let worktree-after-task
      (nefor.node.rename "worktree"
        (nefor.node.*> (str id ".create-worktree") worktree-trigger worktree)))

    ;; fanout gives the same Task to both nodes and joins their outputs into the
    ;; ordered product Task + Worktree. The builder cannot run before both exist.
    (let builder-input
      (nefor.node.rename "input"
        (nefor.node.fanout (str id ".input") task-value worktree-after-task)))
    (let policy
      (nefor.contracts.da-policy
        (assoc (as (Map String String) {}) (get config "build") "deny")))
    (let builder
      (nefor.node.rename "builder"
        (nefor.actors.agent agents.resolve-model
          (as (nefor.actors.AgentConfig agents.Model)
            {:id (str id ".builder")
             :model agents.standard
             :system
               (str "Implement the task in its worktree. Do not run "
                 (str (get config "build")
                   "; the workflow runs it deterministically."))
             :tools nefor.actors.general-tools
             :da-policy policy
             :max-corrections 2})
          (type-tag (+ nefor.contracts.Task nefor.worktree.Worktree))
          (type-tag nefor.contracts.TextAnswer))))
    (let compile
      (nefor.node.rename "build"
        (nefor.shell.run (str id ".build")
          (as nefor.shell.ShellScriptParams
            {:script (get config "build")
             :cwd (get config "worktree")
             :timeout (nefor.contracts.no-timeout)}))))
    (let builder-answer
      (nefor.node.rename "answer"
        (nefor.graph.identity (str id ".builder-answer")
          (type-tag nefor.contracts.TextAnswer))))
    (let compile-after-builder
      (nefor.node.rename "compile-after-builder"
        (nefor.node.*> (str id ".compile-after-builder")
          builder-answer compile)))
    ;; ProcessResult includes stdout, stderr, and a typed exit-or-signal sum.
    ;; A failed command is business data, not an exception. This reviewer may
    ;; approve it or return NeedChanges according to this workflow's policy.
    (let reviewer
      (nefor.node.rename "reviewer"
        (nefor.agents.with-tools agents.resolve-model agents.standard (str id ".reviewer")
          "Review the deterministic build result. Return Approved or NeedChanges."
          nefor.actors.read-only-tools
          (type-tag nefor.contracts.ProcessResult)
          (type-tag ReviewDecision)
          2)))
    (let prepared (nefor.node.>>> builder-input builder))
    (let compiled
      (nefor.node.>=> prepared
        (nefor.node.lift-result (str id ".build-result") (type-tag nefor.contracts.AgentError) compile-after-builder)))
    ;; `named` is the deliberate abstraction boundary. The sidebar presents
    ;; this workflow as one expandable node while preserving all nested stages.
    (nefor.node.named id (nefor.node.>=> compiled reviewer))))

(let development-task
  (nefor.actors.task-source "development-task"
    "Implement and review the requested repository change."))
(let development
  (development-workflow
    (as DevelopmentConfig
      {:id "development"
       :repository "."
       :worktree "tmp/mag-book-worktree"
       :branch "mag-book-work"
       :base "main"
       :build build-command})))
(let developed (nefor.node.>>> development-task development))

;; ------------------------------------------------------------
;; 4. Fixed parallelism stays in the compile-time universe
;; ------------------------------------------------------------

;; `sequence` receives a MAG List of nodes. Its length and order are known now,
;; so the result is an ordinary List with the same fixed order even if runtime
;; answers arrive out of order. Each agent's AgentError remains an ordinary
;; element alternative, so the result below is
;; Node ProcessResult (List (TextAnswer | AgentError)). No dynamic collection
;; concept is involved.
(let audit-one
  (nefor.agents.with-tools agents.resolve-model agents.standard "audit-one" "Audit correctness." []
    (type-tag nefor.contracts.ProcessResult)
    (type-tag nefor.contracts.TextAnswer) 1))
(let audit-two
  (nefor.agents.with-tools agents.resolve-model agents.standard "audit-two" "Audit maintainability." []
    (type-tag nefor.contracts.ProcessResult)
    (type-tag nefor.contracts.TextAnswer) 1))
(let fixed-audits
  (nefor.node.sequence "fixed-audits" [audit-one audit-two]))

;; Unit-input nodes may be composed before they are connected. For example,
;; sequencing independently constructed task sources creates one outer
;; Node Unit (List Task). Only that outer unfed boundary is activated; the
;; nested sources are fed by the sequence routes and do not start twice.
(let audit-tasks
  (nefor.node.sequence "audit-tasks"
    [(nefor.actors.task-source "correctness-task" "Audit correctness.")
     (nefor.actors.task-source "maintenance-task" "Audit maintainability.")]))

;; `parallel` maps two independent product components. `fanout`, `parallel`,
;; `choose`, `sequence`, `>>>`, `>=>`, and `*>` are functions returning Node.
;; Use them when they clarify the program; a one-off graph need not invent an
;; abstraction merely to avoid a repeated line.

;; ------------------------------------------------------------
;; 5. Runtime multiplicity is a different effect
;; ------------------------------------------------------------

(type Followup {:title String :instructions String})
(type Finding {:title String :finding String})
(type FinalSummary {:summary String})

;; DynamicList T means that cardinality is discovered while Nefor runs. It is
;; only a node-boundary effect, never a runtime-sized MAG List value.
(let planner
  (nefor.agents.dynamic-with-tools agents.resolve-model agents.standard "planner"
    "Return the ordered follow-up investigations."
    nefor.actors.read-only-tools
    (type-tag ReviewDecision) (type-tag Followup) 2))

;; Runtime-dependent values are represented by typed references. These calls
;; build a closed expression graph; they do not execute against an occurrence.
(let occurrence
  (nefor.dynamic.trigger-ref (type-tag (nefor.dynamic.Indexed Followup))))
(let collection (nefor.dynamic.field-ref occurrence "collection" (type-tag String)))
(let index (nefor.dynamic.field-ref occurrence "index" (type-tag Int)))
(let followup (nefor.dynamic.field-ref occurrence "value" (type-tag Followup)))
(let instructions
  (nefor.dynamic.field-ref followup "instructions" (type-tag String)))
(let index-text (nefor.dynamic.int-to-decimal-string-ref index))
(let worker-id
  (nefor.dynamic.concat-strings-ref
    [(nefor.dynamic.capture-ref "followup.worker." (type-tag String)) index-text]))
(let worker-root
  (nefor.dynamic.concat-strings-ref
    [(nefor.dynamic.capture-ref "followups-" (type-tag String)) index-text]))
(let worker-template
  (nefor.agents.dynamic-template-with-tools agents.resolve-model agents.standard
    "followups" collection index worker-id worker-root instructions
    nefor.actors.read-only-tools (type-tag Finding) 2))

(let workers
  (nefor.dynamic.traverse-template "followups" worker-template
    (type-tag Followup)
    (type-tag (core.types.Result nefor.contracts.AgentError Finding))))

(let result-context
  (nefor.dynamic.context "followup-context"
    (type-tag (core.types.Result nefor.contracts.AgentError Finding))))
(let integrator
  (nefor.agents.with-tools agents.resolve-model agents.standard "integrator"
    "Integrate every ordered finding into one summary."
    nefor.actors.read-only-tools
    (type-tag nefor.contracts.ProviderInput)
    (type-tag FinalSummary) 2))
(let integrate (nefor.node.>>> result-context integrator))

;; ------------------------------------------------------------
;; 6. The large workflow retains the hierarchy we chose
;; ------------------------------------------------------------

(let planned (nefor.node.>=> developed planner))
(let investigated
  (nefor.node.>=> planned (nefor.node.lift-result "workers-result" (type-tag nefor.contracts.AgentError) workers)))
(let production (nefor.node.>=> investigated integrate))
(let result (nefor.graph.output-for "result" production))

;; A normal Nefor program has one completion form. `compile` applies this pure
;; Graph -> Graph function to the empty graph, validates the complete topology,
;; and lowers it into the immutable artifact the runtime executes.
(nefor.artifact.compile
  (fn [[graph nefor.graph.Graph]] -> nefor.graph.Graph
    (nefor.graph.add-edges graph
      [(nefor.graph.edge production result)])))
```

The important scale transition is not a new graph language. `development-workflow`
is an ordinary function returning one node; its callers do not need to know that
it creates a worktree, an agent, a deterministic build, and a reviewer. `named`
records that meaningful boundary, while `>>>` and `>=>` remain transparent. The
run therefore shows its direct pipeline immediately; expanding `development`
reveals its stages, and expanding `builder` reveals the agent's `entry`, `llm`,
`run-tool`, and `tool-result` nodes.

Logical names are local path segments, independent of opaque runtime actor ids.
`rename` changes only the displayed segment. A full path such as
`["development" "builder" "llm"]` must be unique in one run; a dot inside an
actor id does not create a hierarchy level.

Use `List (Node I O)` with `sequence` when the number of workers is known while
MAG compiles. Use `DynamicList` only when runtime data determines cardinality.
Errors remain typed values in either case: a workflow may preserve them, retry
them with a bounded retry node, branch on them, or make them part of its business
result according to the task.
